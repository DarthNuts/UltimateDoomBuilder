# План: ZT Workbench — UDB для дизайнера и облачная ИИ-машина

Цель:
- **Дизайнер работает только в UDB.** Там у него карты, скрипты, ресурсы мода, запуск игры, две кнопки git
  («Отправить свежие правки», «Получить свежие правки») и чат с ИИ. SLADE, распаковка билдов и ручная работа с git
  не нужны.
- **ИИ (Claude) живёт на облачной машине с Ubuntu.** Туда из WSL переезжает проект. Там сборка, проверки,
  слияния веток и сессии ИИ — и владельца, и дизайнера.
- Основа инструмента — форк UDB. MCP-сервер ([mcp-plan.md](mcp-plan.md)) — одна из частей.

Источники анализа:
- история репозитория мода: 7 снимков билдов дизайнера (15.07–24.09.2026), наши коммиты, плейбуки
  `docs/mod-workflows.md`, `docs/migration-plan.md`;
- исходники форка; ссылки `файл:строка` — по форку.

## 1. Опыт проекта

### 1.1 Что присылал дизайнер: 7 билдов, 15.07–24.09.2026

- **Графика** — почти в каждом билде: спрайты, Hires, брайтмапы, текстуры (PNG).
  - Массовые переносы: 675 брайтмапов (06.08), 401 файл Hires (14.08).
  - Часть спрайтов — PNG без расширения (`sprites/eff/missiles/POW1F0`): так файлы кладёт SLADE.
- **Звук:** OGG, часто без расширения (`SOUNDS/SECDRON1`, 35 файлов `earthboss/` и `thessboss/` в 24.09); 33 WAV
  заменены на OGG; правки `SNDINFO`.
- **Код:** DECORATE во всех билдах, ZScript в 5 из 7 (13 новых `.zc` босса T'Hess в 24.09), `GLDEFS` в 5 из 7;
  `LANGUAGE`, `ZMAPINFO`, `menudef.txt`, `ANIMDEFS`; шейдеры и материалы (`.fp`), скины моделей.
- **Карты** — `TEXTMAP` и `SCRIPTS.acs` MAP01–MAP03 в 6 из 7 билдов.
- **Ошибки, которые ловили руками:**
  - 174 дубля `* (1).*` на 78,7 МБ (24.09);
  - имя файла с кириллической «В»: `Graphics/HELВ.png` (17.08);
  - удалённые спрайты, на которые ещё ссылался `.dec` (анимация дробовика);
  - правки линий, затёртые пересохранением карты (линия 6957 MAP01).

### 1.2 Главная боль приёма — TEXTMAP

UDB при сохранении перенумеровывает элементы, поэтому `TEXTMAP` переписывается почти целиком:

| Билд | MAP01, строки | MAP02, строки |
|---|---|---|
| 26.07 | +162 / −85 | +37 707 / −36 632 |
| 17.08 | — | +17 949 / −15 723 |
| 24.09 | +201 892 / −188 976 (всего в файле 495 839) | +98 431 / −91 023 |

Построчный 3-way merge на таких диффах бесполезен, поэтому наши правки (двери, лифты, ловушки) сверяли точечно
вручную. Та же перенумерация ломает `aline` и `bline` дверей. Без семантического слияния карт (§8.2) две кнопки
работать не будут: первое же «Получить» после правки карты с двух сторон даст конфликт на сотни тысяч строк.

## 2. Ветки и две кнопки

### 2.1 Ветки и рабочие копии

У каждого человека две рабочие копии одной и той же ветки: на Windows — для UDB, на машине в своём профиле Linux —
для своего Claude. Обмениваются они через голый репозиторий на машине.

| Человек | Пользователь Linux | Ветка | Рабочие копии |
|---|---|---|---|
| владелец | `dev` | `dev` | Windows (UDB) и `/home/dev/projects/ZeroTolerance` (его Claude) |
| дизайнер | `design` | `design` | Windows (UDB) и `/home/design/projects/ZeroTolerance` (его Claude) |

`main` — чистая линия: в неё попадает только слияние `dev` → `main` или `design` → `main` по команде владельца.
Проверки и черновики остаются в `dev` и `design` (решение 10.11.2026).

- **Синхронизация `main` → `dev` и `design`.** После слияния в `main` хук сам вливает `main` в рабочие ветки, если слияние
  проходит без конфликтов; карты сливаются семантическим драйвером (§8.2). ИИ для этого не нужен. При конфликте
  ветка не трогается, а владелец получает уведомление и сводит сам или своим Claude. Поэтому у дизайнера
  «Получить» — почти всегда простая перемотка вперёд.
- **Слияние `dev` → `main` и `design` → `main`** — по команде владельца, его Claude: семантическое слияние карт,
  проверки, коммит.
- **Права веток** проверяет хук голого репозитория по пользователю Linux, от которого пришёл push:
  - `dev` — любые ветки;
  - `design` — только `design` и свои временные `design-*`, без удаления и перезаписи истории.
- **GitHub — зеркало голого репозитория.** После каждого push на машину все ветки уходят на GitHub (ветки на
  GitHub при этом не удаляются). Правило «пуш только по слову» снято 10.11.2026: оно было нужно, чтобы не мешать
  дизайнеру, а теперь у него своя ветка.

### 2.2 «Отправить свежие правки»

1. Сохранить карту и открытые скрипты.
2. Быстрые проверки (§12): имена только из ASCII, нет дублей `* (1)`, нет огромных файлов. Это предупреждение, а не
   запрет.
3. Коммит всех изменений. Сообщение собирается само: какие карты и сколько в них изменено линий, секторов и вещей
   (по семантическому diff), какие файлы. Плюс необязательная строка комментария.
4. Push в свою ветку. Если на сервере уже есть новые коммиты — сначала «Получить», затем push.
5. Хук после push прогоняет проверки и собирает WAD и pk3 — от имени того, кто отправил, в отдельной папке его
   профиля `~/ci/`. Рабочую копию, где работает его Claude, хук не трогает. Итог приходит в панель чата: «проверки
   пройдены» или «ошибка в `<файл>`, строка N», плюс ссылки на WAD и pk3.

### 2.3 «Получить свежие правки»

1. Сохранить. Неотправленные правки — локальный коммит: они не теряются и никуда не уходят.
2. `fetch` и слияние своей ветки с сервера.
3. `TEXTMAP` сливается семантическим драйвером (§8.2); плагин прописывает его в конфиг репозитория при
   подключении.
4. Конфликты:
   - **на карте** — подсвечиваются в UDB, выбор «моё / с сервера» по элементу;
   - **в текстовом файле** — окно: «оставить моё», «взять с сервера», «попросить ИИ свести». В последнем случае
     локальное состояние уходит во временную ветку, свой Claude сводит её в рабочей копии на машине, человек снова
     жмёт «Получить»;
   - **в PNG, OGG и других двоичных** — «моё / с сервера».
5. Ресурсы и карта перечитываются на месте (§9). Сводка: что пришло — сообщения коммитов.

### 2.4 Подключение — один раз

Пользователя на машине заводит владелец (или я под root по его просьбе). Человек создаёт свой SSH-ключ и отдаёт
владельцу только публичную часть.

Окно «Подключить проект» в UDB: адрес машины, пользователь Linux, путь к ключу. Дальше плагин всё делает сам:
1. проверяет вход по SSH;
2. клонирует репозиторий с машины (649 МБ) и переключается на свою ветку;
3. прописывает драйвер слияния карт и настройки git для проекта. Автор коммитов — имя и noreply-адрес человека
   с GitHub, чтобы в истории было видно, кто что сделал. Те же имя и адрес — у его Claude на машине;
4. открывает проект в UDB.

Аккаунт GitHub для обмена не нужен: и git, и чат идут по одному SSH-ключу к машине.

Что для этого нужно на ПК:
- **git** — портативный MinGit рядом с UDB, его можно распространять с приложением; ставить ничего не надо;
- **SSH** — встроенный в Windows клиент OpenSSH (`C:\Windows\System32\OpenSSH\ssh.exe`; у владельца версия 9.5).
  На ПК дизайнера — проверить при подключении;
- **`.gitattributes`** в репозитории — до первого клона на Windows. Сейчас его нет, а git на Windows по умолчанию
  переводит окончания строк в CRLF, и `TEXTMAP` со скриптами поедут. Нужны `* -text` и явные `binary`.
  `menudef.txt` остаётся CRLF, как требует мод. Имён, различающихся только регистром, и не-ASCII имён в
  репозитории сейчас нет — проверено.

## 4. Чат в UDB

### 4.1 Как устроен

Отдельного сервиса на машине нет. Панель в UDB через SSH запускает немодифицированный Claude Code этого же
пользователя в его рабочей копии:

```
UDB на Windows                              машина, пользователь dev или design
  панель чата ── ssh.exe, свой ключ ──────▶ claude -p (поток JSON) в ~/projects/ZeroTolerance
  MCP живой карты ◀── обратный порт ssh -R ─ Claude
  файлы и сборки ◀── sftp ────────────────── ~/out, ~/ci
```

- **Команда:** `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages
  --resume <сессия> --permission-mode acceptEdits --mcp-config <конфиг>`, рабочая папка — клон пользователя. По сути
  это работа в терминале по SSH, только окно — в UDB.
- **Стоп** — SIGINT: ход завершается чисто. SIGTERM ход не сохраняет.
- **История** — `--resume` по id сессии; список сессий — файлы `~/.claude/projects/<папка>/*.jsonl`.
- **Разрешения.** `--permission-prompt-tool` отправляет запрос в MCP-инструмент. Этот инструмент отдаёт сам UDB
  через обратный порт, а панель показывает «Разрешить / Отклонить». Формат ответа инструмента в документации не
  найден — проверить на спайке. Запасной вариант: список разрешённого (`--allowedTools`), остальное отклоняется.
- **Обратный порт** `ssh -R` открывается на `127.0.0.1` машины. Порт на localhost видят все пользователи машины,
  поэтому MCP-сервер UDB принимает только запросы с токеном. Токен лежит в конфиге MCP в профиле пользователя
  (права 600).
- **Файлы и сборки** — `sftp` по тому же ключу, с докачкой (`reget`).
- **Формат потокового ввода** `stream-json` в справке CLI не описан (описан формат сообщений SDK) — проверить на
  спайке.

### 4.2 Панель

Панель — докер UDB (`General.Interface.AddDocker`, как у плагина 3D Floor Mode):
- ввод запроса, ответ потоком, кнопка «Стоп»;
- шаги ИИ в свёрнутом виде: «читает …», «правит `src/actors/…`», «запускает `build-wad.py`»;
- запросы разрешений — кнопки «Разрешить» и «Отклонить»;
- вложения: выделенное на карте (номера и поля), картинка области карты, файл проекта, скриншот;
- перед запросом: отправить неотправленные правки из UDB (галочка; включена, если есть что отправлять) и обновить
  рабочую копию на машине. Тогда Claude видит ровно текущее состояние;
- история: новый чат или продолжить прежний.

### 4.3 Что приходит обратно

- **Правки файлов проекта** Claude коммитит в свою ветку и отправляет в голый репозиторий (когда — §5.2). В чате
  появляется кнопка «Получить свежие правки».
- **Отдельные файлы** (картинка, отчёт) Claude кладёт в `~/out` — в чате карточка «Скачать / Открыть».
- **Сборка** — «Скачать WAD» (23 МБ) и «Скачать pk3» (484 МБ):
  - с докачкой и проверкой хеша;
  - не качается заново, если не изменилась;
  - кладётся в папку GZDoom на ПК.

  Для своих тестов pk3 качать не обязательно: в режиме проекта Test Map грузит `src/` как папку — GZDoom это
  умеет. Готовые WAD и pk3 нужны, когда требуется именно сборка с машины.
- **Живая карта.** Claude видит и правит карту, открытую в UDB: инструменты из [mcp-plan.md](mcp-plan.md) через
  обратный порт того же SSH-соединения. Входящие порты на ПК не нужны.

## 5. Учётные записи и правила

### 5.1 Учётные записи Claude

Факты из документации Claude Code (code.claude.com/docs):
- **Условия использования** (`legal-and-compliance`):
  - подписка Claude — личная, каждый входит своими учётными данными;
  - сторонним разработчикам нельзя встраивать вход claude.ai в свои приложения и быть посредником в чужом
    использовании Claude;
  - для приложений на Agent SDK документация рекомендует ключ API;
  - входить своей подпиской в немодифицированный Claude Code можно.
- **Учётные данные** лежат в `~/.claude/` пользователя Linux (файл с правами 600).
- **Claude Desktop умеет сессии по SSH** на Linux-машину (вкладка Code; на Windows нужен OpenSSH 9.4+). Свою копию
  Claude Code он ставит в `~/.claude/remote/` пользователя, около 1 ГБ. Ограничения: нет встроенного браузера,
  панель файлов только для просмотра.
- **В режиме `-p`** заданный `ANTHROPIC_API_KEY` всегда побеждает подписку.
- **Песочница** для команд оболочки на Linux есть (bubblewrap, `sandbox.enabled`). Режим без разрешений
  (`bypassPermissions`) документация допускает только в изолированной среде без интернета.

Как это ложится на схему с двумя пользователями:
- У каждого человека свой пользователь Linux, свой SSH-ключ, свой вход в Claude в своём профиле и своя подписка.
  Это прямо разрешённый случай: человек входит своей подпиской в немодифицированный Claude Code. Панель UDB лишь
  показывает его Claude в окне.
- Agent SDK не используем: для приложений на нём документация рекомендует ключ API. CLI покрывает всё нужное.
- Вход делает сам человек, один раз: `claude` в SSH-терминале, вход по ссылке.
- В профилях не задаём `ANTHROPIC_API_KEY`, чтобы он не перебил подписку.
- Дизайнеру нужна своя подписка: Pro, Max или место в Team.
- Фоновым задачам машины (синхронизация веток, проверки после push) Claude не нужен: это обычные скрипты.

| Кто | Окна | Учётная запись |
|---|---|---|
| владелец, `dev` | чат в UDB, Claude Desktop по SSH, терминал | своя подписка |
| дизайнер, `design` | чат в UDB; до готовности панели — Claude Desktop по SSH | своя подписка |

### 5.2 Правила

- Права веток — хук (§2.1). Профили закрыты друг от друга, `sudo` нет, вход только по ключам.
- Песочница bubblewrap для команд оболочки — включить. Режим без разрешений не используем.
- Правила работы Claude у каждого свои, в его памяти. У владельца: коммит — по слову «коммит», после коммита — сразу
  push в голый репозиторий машины. Отдельного слова «пуш» больше не нужно. Оттуда хук зеркалирует ветки на GitHub.
- Резервные копии — снимки диска Contabo и зеркало на GitHub.

## 6. ZScript: редактор и проверка

**Что есть:**
- тип скрипта `ZSCRIPT` (`ScriptConfiguration.cs:60`) и подсветка по `ZDoom_ZSCRIPT.cfg`; тип файла редактор
  узнаёт по содержимому (`ScriptTypeParserSE.cs`: `class X : Y {` — ZScript);
- классы вкладок для файла с диска (`ScriptFileDocumentTab`) и для файла из ресурса (`ScriptResourceDocumentTab`);
- свой разбор ZScript (`ZScriptParser.cs`): классы-акторы, свойства, состояния — для списка вещей и спрайтов. Тела
  функций он пропускает, типы не проверяет.

**Чего нет — способа открыть файл.** Редактор скриптов (F10, кнопка Script Editor) показывает только лампы карты
из игровой конфигурации: `SCRIPTS` (ACS) и `DIALOGUE` (USDF). 31.12.2019 upstream убрал:
- команду «Open File» (e61937c7, «Removed the capability to open any file from the script editor»);
- вкладку Script Navigator с деревом текстовых ресурсов (e0922352, «Removed the remains of resource editing»,
  −1351 строка; среди удалённого — `ScriptResourcesControl`).

Диалог `openfile` в форме редактора остался, но ни к чему не подключён. Вернуть: взять эти два коммита за
основу (откат с доработкой под текущий код) — дерево ресурсов проекта и «Открыть файл».

**Чего нет — компилятора.**

В конфигурации ZScript нет ключа `compiler`. Компилятор ZScript — часть движка на C++, переносить его в C#
неподъёмно и бессмысленно.

**Что сделать — «GZDoom как компилятор»:**
- Класс компилятора рядом с `AccCompiler` вызывает
  `gzdoom.exe -iwad … -file <порядок загрузки мода> -norun +logfile <лог>`.
  - Ключи `-norun`, `-stdout`, `logfile` в нашем `gzdoom.exe` есть — проверено по строкам бинарника.
  - Выходит ли `-norun` **после** компиляции ZScript — проверить на спайке.
- Разбор лога: `Script error, "<ресурс>:<путь>" line N` превращается в ошибку с файлом и строкой, путь
  сопоставляется с файлом в `src/`, клик открывает строку. Для ACS этот механизм уже есть.
- Окно Fatal Error на Windows: логика `capture_crash.ps1` — текст ошибки в лог, закрыть окно, таймаут.
- Без сборки pk3: GZDoom грузит папку как ресурс (`-file <папка>`), значит проверять можно прямо `src/`.
- После разделения ролей это в первую очередь проверка у дизайнера до отправки. Полную проверку после каждой
  отправки всё равно делает машина.

## 7. Ресурсы мода и pk3

**Факты:**
- Ресурсами могут быть pk3, pk7, WAD и папки. Код записи сохранился: `PK3Reader.SaveFile` (`PK3Reader.cs:662`),
  `DirectoryReader.SaveFile` (`DirectoryReader.cs:513`), сохранение вкладки ресурса со сверкой MD5
  (`ScriptResourceDocumentTab.cs:96-116`).
- С мая 2021 года все ресурсы открываются только на чтение: `DataManager.cs:400,411,416`, upstream e9805238
  («Resources are now always opened as read-only. Fixes #559»).
- Запись в pk3 перепаковывает весь архив в памяти и переписывает файл (`PK3Reader.cs:694-722`). Наш
  `ZeroTolerance.pk3` — 484 МБ.

**Что сделать:**
- Подключать `src/` рабочей копии ресурсом-папкой с флагом «проект, можно править». Read-only снимается только с
  неё; вкладки пишут прямо в файлы, сверка MD5 перед записью уже есть.
- В pk3 не писать: pk3 — только артефакт сборки.
- **Хвостовые пробелы.** UDB срезает их при каждом сохранении скрипта (`ScriptDocumentTab.cs:207`). Они есть в 39
  из 108 файлов ZScript и DECORATE мода — первое же сохранение из UDB даст шум в диффе и лишние конфликты. Сделать
  опцией, для файлов проекта по умолчанию выключить.
- **Вкладка файла с диска** (`ScriptFileDocumentTab.Save`, строки 106-115) пишет без сверки и затрёт пришедшую
  через «Получить» правку. Нужна сверка, как у ресурсов, плюс слежение (§9).

## 8. Карты: режим проекта и семантическое слияние

### 8.1 Карта прямо из `wad-src/`

Сейчас UDB открывает только `.wad` (`MainForm.cs:742`). Для двух кнопок карта должна жить в файлах рабочей копии.
- **Файл проекта** `zt-project.json` в корне репозитория: пути `src/`, `wad-src/`, `wad_structure.json`, порядок
  загрузки из `ZeroTolerance.bat`, адрес машины. Папка GZDoom и IWAD — в локальных настройках UDB.
- **Открыть карту.** Временный WAD собирается из `wad-src/MAPxx/` по `wad_structure.json`: `TEXTMAP`, `SCRIPTS.acs`
  (как ламп `SCRIPTS`), `BEHAVIOR.lmp`, `DIALOGUE.lmp`. Дальше UDB работает как обычно — он и так держит карту во
  временном WAD.
- **Сохранить.** Лампы пишутся обратно в файлы `wad-src/MAPxx/`, `BEHAVIOR.lmp` — из компиляции UDB.

### 8.2 Семантический diff и merge карт

Сравниваются не строки, а элементы:
- **сопоставление:** вершины — по координатам; линии — по паре координат концов; стороны — по линии и стороне;
  секторы — по набору граничных линий; вещи — по типу, координатам и `id`;
- **3-way по полям:** правка с одной стороны принимается; одно поле, изменённое по-разному, — конфликт;
- **новые и удалённые элементы** — по совпадению геометрии.

Где работает:
- драйвер слияния git (`.gitattributes`: `TEXTMAP merge=udmf`) — у дизайнера в «Получить» и на машине при
  синхронизации и слиянии в `main`;
- читаемый git diff (`diff=udmf`) — сообщения коммитов «Отправить» и отчёты ИИ;
- конфликты на карте в UDB.

Реализация — одна: библиотека C# под .NET Standard 2.0. Её подключает плагин UDB (.NET Framework 4.7.2 это
умеет), а консольная утилита на её основе собирается под Linux и Windows самодостаточным файлом, без установки
.NET. .NET SDK 10 у владельца уже стоит. Python не годится: у дизайнера на Windows его нет.

## 9. Подмена файлов на лету

### 9.1 Как UDB держит файлы (факты)

| Файл | Как открыт | Что будет при внешней записи |
|---|---|---|
| WAD карты | лампы карты копируются во временный WAD, исходник закрывается (`MapManager.cs:410-436`). Как ресурс тот же WAD открыт на чтение с `FileShare.ReadWrite` (`WAD.cs:236-247`) | перезапись на месте проходит; замена через переименование отклоняется (нет `FileShare.Delete`). UDB изменения не видит |
| pk3-ресурсы | открываются на чтение по требованию (`PK3Reader.cs:189-219`) | перезапись проходит, список файлов устаревает |
| Вкладки скриптов с диска | читаются один раз | сохранение молча затирает внешнюю правку |
| Карта в памяти | — | не перечитывается; смена карты стирает историю отмены (`General.cs:1332`) |

Полезное уже есть: Reload Resources (`MapManager.cs:2383`) перечитывает ресурсы, сохраняя карту и отмену, и умеет
запускать команды до и после себя. Слежения за файлами в ядре нет.

### 9.2 Что сделать

После «Получить» меняются файлы рабочей копии, и UDB должен подхватить их сам:
- **слежение** (`FileSystemWatcher` с задержкой около секунды) за `src/` и `wad-src/`;
- **ресурсы** — Reload Resources;
- **вкладки скриптов:** без несохранённых правок — перечитать молча; с правками — «оставить моё / взять с диска /
  показать разницу»;
- **карта:**
  - правок в UDB нет — перечитать на месте с сохранением вида, режима и выделения, одним шагом отмены. Разница
    (§8.2) применяется через обычное API карты, чтобы история отмены записала только изменённое;
  - правки есть — до слияния дело не дойдёт: «Получить» сначала сохраняет и коммитит;
  - число элементов сильно поменялось — полная замена, тоже одним шагом отмены.

## 10. Человек и ИИ одновременно

У каждого человека — свой Claude в своём профиле на машине; схема одна и та же для владельца и дизайнера.
- **Файлы.** Claude правит свою рабочую копию на машине, в своей ветке; человек забирает правки кнопкой
  «Получить».
- **Живая карта** — через MCP по обратному порту SSH (§4.1). Каждая правка Claude — шаг отмены, ревизия карты
  отсекает правки по устаревшим номерам ([mcp-plan.md](mcp-plan.md)). Дополнить:
  - правка Claude ждёт, пока человек не закончит действие (перетаскивание, рисование);
  - журнал правок Claude в панели чата с кнопками «показать» и «откатить»;
  - правки Claude подсвечены на карте до следующего действия человека.
- **Вопросы в обе стороны:** Claude спрашивает через панель (кнопки вариантов); человек прикладывает к запросу
  выделенное на карте.

## 12. Проверки проекта

Набор один, запускается в двух местах: быстрая часть — у дизайнера перед «Отправить», полная — на машине после
каждой отправки. Каждая проверка — из реального случая:
- спрайты, на которые ссылаются состояния DECORATE и ZScript, есть в `src/` (анимация дробовика);
- звуки из `SNDINFO` есть на диске; звуки акторов описаны в `SNDINFO`;
- ключи `LANGUAGE` из MENUDEF и кода есть в `LANGUAGE.csv`;
- нет дублей `* (1).*` и одинаковых файлов под разными именами;
- имена файлов только из ASCII (`HELВ.png`);
- окончания строк по правилам мода (`menudef.txt` — CRLF);
- ссылки линий и вещей на ACS-скрипты (`check_script_refs` из плана MCP);
- на машине дополнительно: `check-acs.py`, `check-zscript.py`, `tools/extra.py check`, сборка WAD и pk3.

## 16. Риски

- **Семантическое слияние ошибается** на сильно перестроенной геометрии. Тогда — конфликт с показом на карте, а не
  тихое решение. Проверка — на исторических слияниях (этап 2).
- **GZDoom без видеокарты.** Если с программным OpenGL проверка или снимки не пойдут — машина с GPU или
  проверки на ПК (спайк 0а).
- **Другая версия `acc` под Linux** даст другой `BEHAVIOR`. Критерий — байт в байт (спайк 0б).
- **pk3 на 484 МБ** по сети: докачка, без повторной загрузки неизменившегося; для тестов дизайнеру хватает `src/`
  папкой.
- **Машина из интернета.** Открыт только SSH, вход по ключам, права веток — хуком. Потеря машины — снимки диска
  Contabo и зеркало на GitHub.
- **Дизайнер отправил поломанное.** `main` это не задевает: слияние — по решению владельца, проверки сразу пишут в
  чат.
- **3D-работа** (Blender, Hunyuan) остаётся на ПК владельца, через машину не идёт.
- **Условия Claude.** Каждый человек входит своей подпиской в немодифицированный Claude Code в своём профиле.
  Подписку одного другому не отдаём; дизайнеру нужна своя.
- **Общий localhost.** Обратный порт MCP на `127.0.0.1` машины видят оба пользователя — MCP-сервер UDB принимает
  только запросы с токеном из профиля владельца этого UDB.
- **Две рабочие копии у человека** (Windows и машина) на одной ветке могут разойтись. Перед запросом в чат панель
  отправляет правки из UDB и обновляет копию на машине; Claude отправляет свои коммиты сразу (решение 6).
- **Нативная часть UDB** (`BuilderNative.dll`) не трогается — сборка без Visual Studio остаётся рабочей.
