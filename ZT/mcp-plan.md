# План: MCP-сервер в Ultimate Doom Builder

Задача: дать агенту (Claude Code и другим MCP-клиентам) доступ к **открытой в UDB карте** — читать, находить,
показывать дизайнеру, править с отменой, проверять, компилировать скрипты, снимать картинку. Сейчас всё это
делается вслепую: Python-скриптами по `TEXTMAP` и скриншотами окон UDB от пользователя.

Это одна из частей общего плана инструмента — [workbench-plan.md](workbench-plan.md).

План опирается на работу над Zero Tolerance (двери, лифты, лестницы, карты из ROM, радар) — какие операции там
повторялись и где ошибались. Для каждого инструмента указано, на что в UDB он опирается.

---

## 2. Архитектура

- **Плагин `ZTMcp`** в форке (`Source/Plugins/ZTMcp`, как остальные плагины). В меню: сервер Off / Read-only /
  Read-write и индикатор подключения в строке состояния. По умолчанию Off.
- **Транспорт — MCP Streamable HTTP** на `127.0.0.1:<порт>/mcp`, JSON-RPC 2.0 (`initialize`, `tools/list`,
  `tools/call`). Claude Code подключается так: `claude mcp add --transport http udb http://127.0.0.1:<порт>/mcp`.
  - UDB запускает пользователь, поэтому stdio-сервер (который запускает клиент) не подходит.
  - .NET Framework 4.7.2: `HttpListener` и JSON (`JavaScriptSerializer` из `System.Web.Extensions`) уже есть в
    системе, новых зависимостей нет.
  - Готового C# SDK для MCP под .NET Framework 4.7.2 нет. Протокола нужно немного, пишем сами.
- **Безопасность:**
  - только `127.0.0.1`;
  - токен в заголовке, генерируется плагином и показывается в меню для копирования;
  - правки — только в режиме Read-write;
  - **сохранение карты и запуск игры — только инструментами с явным подтверждением в окне UDB.**
- **Потоки.** Все обращения к карте маршалятся в UI-поток (`Control.Invoke`), запрос сервера ждёт результата.
  Дизайнер может работать параллельно: правка агента встаёт между его действиями.
- **Отмена.** Каждый вызов, меняющий карту, — один шаг `UndoManager.CreateUndo("MCP: <инструмент>")`. Ctrl+Z
  дизайнера откатывает правку агента целиком.
- **Ревизия карты** — урок `aline`/`bline`.
  - Каждый ответ несёт `map_revision`: счётчик изменений карты (растёт от любой правки, в том числе
    дизайнера).
  - Правки по номерам элементов принимают `expect_revision`: если карта с тех пор менялась, вызов
    отклоняется с подсказкой перезапросить.
  - Правки по выделению или по запросу (поле, тег, рамка) ревизию не требуют.
- **Ответы компактные:** лимит и постраничность для списков, поля по запросу (`fields: [...]`), координаты как в
  `TEXTMAP`, имена полей UDMF как в `TEXTMAP`. Так результаты MCP и Python-скриптов мода совпадают.

### 3.5 Универсальный выход

| Инструмент | Что делает | P |
|---|---|---|
| `run_udbscript` | выполнить JavaScript с API UDBScript (`Map`, `GameConfiguration`, `Vector2D`…) и вернуть `JSON.stringify` результата. Правки — одним шагом отмены. Только Read-write. Закрывает всё, для чего нет отдельного инструмента | P2 |

Обёртки UDBScript (`MapWrapper` и др.) объявлены `internal`. Нужна одна строка в форке —
`[assembly: InternalsVisibleTo("ZTMcp")]` в UDBScript — или сервер внутри самого UDBScript (решение §5.3).
Так же `internal` в ядре: сохранение карты (`MapManager.SaveMap`) и компилятор (`AccCompiler`). Варианты —
вызывать их через систему действий UDB (`General.Actions.InvokeAction`) или открыть ядро плагину тем же
`InternalsVisibleTo`. Выбрать на спайке.

### 3.6 Предметные инструменты Zero Tolerance (P3, после устойчивых дверей)

Строятся поверх §3.1–3.3. Логика остаётся в Python-скриптах мода (`door_migrate.py`, `lift_migrate.py`), MCP даёт
им живую карту:
- `zt_doors`: двери, половинки, клетки, ошибки разметки;
- `zt_lifts`: кабины, клетки, лестницы.

Дублировать эту логику в C# не нужно.

## 5. Решения — нужны от вас

1. **Транспорт.**
   - Рекомендую HTTP прямо в плагине: одна сущность, работает, пока открыт UDB.
   - Альтернатива — Python-мост (stdio MCP ↔ локальный канал к плагину): зрелый Python SDK, но два процесса.
2. **Права.** Режимы Off / Read-only / Read-write в меню плюс подтверждение в окне UDB для сохранения, запуска
   игры и перезагрузки с потерей правок. Рекомендую так. Альтернатива — подтверждать каждую правку (надёжнее,
   но мешает массовым операциям).
3. **Где сервер.**
   - Отдельный плагин `ZTMcp` с `InternalsVisibleTo` в UDBScript — рекомендую: правки UDBScript минимальны.
   - Альтернатива — встроить в UDBScript: JS-движок под рукой, но плагин разрастается.
4. **`run_udbscript`** — включать ли универсальный JS.
   - Мощно: любое действие без нового инструмента.
   - Но агент получает полный доступ к карте кодом.
   - Рекомендую: только в Read-write и с журналом выполненного кода.
5. **Предметные инструменты ZT в C#** — нет: логика остаётся в Python-скриптах мода, MCP даёт им карту. Рекомендую
   так.

## 6. Риски

- **Смешанные правки агента и дизайнера.** Ревизия карты (§2) отсекает правки по устаревшим номерам. Каждая правка
  агента — отдельный шаг отмены.
- **Долгие операции в UI-потоке** (большие запросы, `render_2d` на всю карту) подвисают интерфейс.
  - Лимиты на размер ответа.
  - Тяжёлое — частями.
  - Рендер — в фоне, если позволит `ImageExporter`.
- **Обновления upstream.** Плагин отдельный, ядро почти не трогаем — сливать upstream легко.
- **Нативная часть.** Плагин на C#, `BuilderNative.dll` не затрагивает — сборка без Visual Studio остаётся рабочей.

## 7. Вне рамок

- Удалённый доступ (не localhost), несколько клиентов одновременно.
- Сетевая игра, запуск игры без подтверждения.
- Замена Python-инструментов мода: они нужны и без открытого UDB (сборка, приём билдов дизайнера).
